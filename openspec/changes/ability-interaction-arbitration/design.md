## Context

### 目标场景与量化约束

本设计必须同时撑住两类场景，它们对系统的要求是不同方向上的极端：

| 维度 | 大型多人 MMO | 高强度 boss 战 |
|---|---|---|
| 实体规模 | 单区域 200~1000+ 可施放实体 | 1 个 boss + 若干 adds + 20~40 玩家 |
| 并发状态层 | 每实体 5~30 层 | **单目标 100+ 层** |
| 申请频率 | 全区域 10²~10³ 次/秒 | 单场 10²~10³ 次/秒，峰值更高 |
| 技能定义 | 10⁴ 量级，**不能全常驻内存** | 同一批定义被高频读取 |
| 带宽 | 每玩家 2~5 KB/s 预算 | boss 状态必须让全员看见 |
| 帧预算 | 技能系统 ≤ 1~2 ms/帧（DS 30Hz） | 同上，但峰值集中在阶段切换 |
| 可用性 | **不停机更新** | 战斗进行中不允许状态损坏 |

### 当前状态

UAK 的执行模型是"一条资产 → 一次施放"：`UAKGameplayAbility` 激活后创建 `UAKAbilityInstance`，由 `UAKAbilityTickTask` 每帧调用 `Tick()`，按 `BuildExecutionPlan()` 展开的扁平调度表推进时间，任务在 `OnTaskStart / OnTaskTick / OnTaskEnd` 中通过 `FAKAbilityContext::SourceASC` 直接落地 GAS 原语。任务有四契约（生命周期 / `Validate` / `GetGASImpact` / Json 双向），资产是纯数据且可双向 Json，已有 `UAKTrace` 溯源、`UAKValidateCommandlet` 门禁、36 个自动化用例与三阶段测试流水线。

### 现有设计的六处不足（本设计要解决的正是这些）

1. **每帧 Tick 的执行模型。** `UAKAbilityInstance` 每帧被无条件 Tick。一个 3 秒技能中间可能有 2.5 秒没有任何事件。上千并发施放 = 每帧上千次空转 Tick，直接吃掉 DS 帧预算。
2. **"复制交给 GAS 就行"在 MMO 下不成立。** GAS 的 `FActiveGameplayEffectsContainer` 为每个 Active GE 复制完整结构，粒度粗、无 AOI、无相关性过滤。boss 身上 100 个 buff 就是复制风暴；而客户端真正需要的只是"我身上有什么、剩多久、数值多少"。
3. **账本的组织方式不支持规模。** 按 `TMap<ASC, Ledger>` 挂在 WorldSubsystem 上，缺实体生命周期分区、缺 LOD、更关键的是**没有区分"服务器完整账本"与"客户端投影"**——归属信息（哪次施放的哪个任务）是服务器内部数据，永远不该发给客户端。
4. **UAsset 不能热更新，也不适合全量常驻。** MMO 必须不停机改数值；10⁴ 量级的技能资产也不能全部加载进内存。
5. **只有单点申请路径。** AOE 打 50 个目标 = 50 次独立的规则查找 + 账本访问 + 裁决 + 落地，没有批量路径。
6. **可观测性与治理在规模下变成数据风暴。** Trace 全量记录会产生海量数据；静态扫描全量重算在 10⁴ 资产下不可行。

这六点决定了：需要的不是"给 ApplyLooseTags 加个计数"，而是一套**分层框架**。

## Goals / Non-Goals

**Goals:**

- **G1** 消灭"一个技能摘掉另一个技能的 Tag"这一类归属错误。
- **G2** 把"谁优先、怎么聚合、上限多少、什么免疫"变成**可热更新的数据**，策划可持续演进且不停机。
- **G3** 在**服务器权威**前提下支撑单区域上千并发施放：实例休眠、事件驱动、对象池化、高频路径无分配。
- **G4** 让副本化状态同步的**带宽可控且可预测**：复制视图 + 相关性 + 增量 + LOD。
- **G5** 支撑单目标上百并发层的高频结算：批量路径、聚合后 GE 数量恒定、阶段集合操作。
- **G6** 让技能冲突在 **CI 里被报出来**，并提供**离线仿真**做回归与平衡分析。
- **G7** 让"这个控制为什么没生效"可溯源到具体归属者与原因，且在规模下采样可控。
- **G8** 提供**可规模化的验证路径**：不变量 + fuzz + 仿真三层，替代组合穷举。

**Non-Goals:**

- **不自建属性系统**。属性的计算与复制仍由 GAS（GE / AttributeSet / Aggregator）负责。UAK 只做"施加之前的决策"与"给客户端看的状态摘要"。
- **不自建网络传输**。复制视图使用 UE 既有的 `FFastArraySerializer` / 属性复制机制，不引入自有传输层。
- **不做客户端状态预测**（本次）。服务器权威下的状态结算以服务器为准；客户端表现层（Montage / Cue）仍走 GAS 自身预测，不退化。
- **不做数值平衡**。上限与递减是护栏，不是平衡方案。
- **不做玩法层 UI**（Buff 图标、状态条）。只提供查询接口与复制视图。
- **不做多角色预览**。那是可视化形态，不解决耦合，优先级低于本 change。
- **不解决单次施放内部的编排问题**（复合、门控、中断顺序）——那是已完成的 M5 能力，本 change 只处理**跨施放**的交互。
- **不做跨服 / 分线 / 存档持久化**。断线重连的状态恢复只做到"服务器账本可从 ASC 重建"，不触及存档层。

## Architecture

### 五层结构

```
┌──────────────────────────────────────────────────────────────────┐
│ L5 治理 Governance                                                │
│   增量冲突扫描 · 不变量 fuzz · 离线仿真回归 · 平衡统计              │
├──────────────────────────────────────────────────────────────────┤
│ L4 观测 Observability                                             │
│   Trace（分级采样）· 编辑器视图 · 调试命令 · 战斗录像与回放         │
├──────────────────────────────────────────────────────────────────┤
│ L3 复制 Replication                                               │
│   复制视图 · 相关性/AOI · LOD · 增量与量化 · 客户端投影             │
├──────────────────────────────────────────────────────────────────┤
│ L2 结算 Resolution                                                │
│   固定步长时钟 · 事件调度 · 状态仲裁 · 归属账本 · 批量结算 · 池化   │
├──────────────────────────────────────────────────────────────────┤
│ L1 数据 Data                                                      │
│   技能定义（编译产物/热更新）· 域配置（版本化）· 流式加载 · 索引     │
└──────────────────────────────────────────────────────────────────┘
      ↑ 贯穿原则：服务器持有唯一真值；客户端看到的一切都是投影
      ↑ 贯穿原则：GE 负责"属性怎么算"，UAK 负责"施加什么 / 给客户端看什么"
```

### 数据流（一次状态申请）

```
任务提交 FAKStatusRequest
   │
   ├─ L1 查域规则（缓存，热更新时换版本）────────────┐
   │                                                  │
   ├─ L2 裁决（纯函数：请求 + 账本 + 规则 → 决议）    │
   │     单点路径 / 批量路径                          │
   │                                                  │
   ├─ L2 落地：Tag / GE / Cue 全部通过 ASC            │
   │     （属性计算与复制仍归 GAS）                    │
   │                                                  │
   ├─ L3 更新复制视图（标记脏、按相关性决定何时发）    │
   │                                                  │
   ├─ L4 采样写 Trace（未采样时零开销）                │
   │                                                  │
   └─ L2 注册到期事件到时间轮（无事件时实例休眠）──────┘
```

### 关键类型

| 类型 | 层 | 职责 |
|---|---|---|
| `UAKStatusDomainConfig` | L1 | 域与规则的**版本化**数据资产，支持热重载与自校验 |
| `UAKAbilityDefinition`（编译产物） | L1 | 技能的紧凑运行时表示，可流式加载、可热替换 |
| `UAKAbilityScheduler` | L2 | 固定步长时钟 + 时间轮 + 休眠实例管理 |
| `FAKStatusRequest` / `FAKStatusResolution` | L2 | 申请与裁决结果（纯数据，池化复用） |
| `FAKStatusLayer` / `FAKStatusLedger` | L2 | 单目标的层集合（含归属，**服务器独有**） |
| `UAKStatusResolver` | L2 | 纯函数裁决；单点与批量两条入口 |
| `UAKStatusSubsystem` | L2 | WorldSubsystem，按实体分区管理账本与生命周期 |
| `UAKStatusReplicationView` | L3 | 每目标的紧凑复制结构（`FFastArraySerializer`），按相关性更新 |
| `UAKRelevancePolicy` | L3 | AOI / 团队 / LOD 的相关性判定与更新频率策略 |
| `UAKSimulationHarness` | L5 | headless 批量仿真：喂输入、跑战斗、出快照与统计 |

## Decisions

### D1 — 服务器持有唯一真值，客户端只持有投影

完整状态账本（含归属者、压制关系、裁决依据）**只存在于服务器**。客户端通过复制视图得到"我身上有什么状态、数值多少、剩余多久"的精简投影。

- **替代：账本双端对称。** 否决——归属与压制关系是服务器内部决策数据，暴露给客户端既浪费带宽又给作弊者可乘之机，且双端一致性维护成本极高。
- **替代：客户端直接从 ASC 的 GE 反推状态。** 否决——GE 结构在客户端不完整（很多 GE 服务端专用），且反推不出"归属"与"被抑制"这类语义。

### D2 — 固定步长时钟 + 事件驱动调度 + 实例休眠

全局以固定步长（如 30Hz）推进；每个施放实例把自己的"下一次需要醒来的时间"注册到时间轮；无事件的实例**完全不 Tick**。持续型任务（`bNeedsTick`）仍需每帧 Tick，但只有它们。

- **替代：维持现有每帧无条件 Tick。** 否决——上千并发施放下，绝大部分 Tick 是空转，直接吃掉帧预算。
- **替代：完全去掉 Tick，一切靠定时器。** 部分否决——持续性任务（引导条件判定、投射物推进、周期 AreaEffect）本质需要每帧驱动；正确做法是**两者并存**：到期靠时间轮，持续任务靠 Tick，而需要 Tick 的实例才进 Tick 列表。
- **结论**：`UAKAbilityInstance` 增加"休眠/唤醒"状态；调度器维护"活跃 Tick 列表"与"到期时间轮"两个结构。固定步长同时保证**确定性与可回放**（D10）。

### D3 — 实例与请求对象池化，高频路径无分配

`UAKAbilityInstance`、`FAKStatusRequest` 等高频对象走对象池复用；裁决路径不分配 `UObject`、不构造 `FString`、不做容器扩容（预分配 + 容量上限）。

- **替代：每次施放 `NewObject`。** 否决——高频施放下 GC 压力与分配开销不可接受，且 GC 停顿在 MMO 中是玩家可感知的卡顿。
- **结论**：池化是 L2 的硬性要求，且必须保证"归还池时彻底重置"（避免脏状态泄漏，这是池化最常见的 bug 源，需用不变量覆盖）。

### D4 — 复制视图与账本分离，且复制视图是紧凑的自定义结构

每目标维护一个 `UAKStatusReplicationView`（`FFastArraySerializer`），元素为 `{状态ID, 档位/数值, 剩余时间（量化）, 来源类别}`，而不是复制完整账本或依赖 GE 复制。

- **替代：直接依赖 GAS 的 ActiveGE 复制。** 否决——粒度粗（每个 GE 一个完整结构）、无 AOI、无相关性、无 LOD，boss 100 层状态下带宽不可控。
- **替代：复制完整账本。** 否决——含归属者指针等服务器内部数据，带宽与安全双重问题。
- **结论**：**分工边界**——属性（血量、护甲、移速）仍由 GAS 的 GE 与属性系统计算并复制；UAK 的复制视图只承载"客户端需要展示的状态列表"。两者不重叠、不重复复制同一份信息。这条边界必须写进文档并长期守住，否则会滑向"两套真值"。

### D5 — 语义层聚合使同类 GE 数量恒定

仲裁在施加前决定最终档位，落地为**单个**聚合后的 GE（或单 GE + SetByCaller）。目标身上某个域的 GE 数量**恒为 1**，无论有多少个来源。

- **替代：施加 N 个 GE，靠 Modifier / Stacking 修正。** 否决——GE 叠加顺序敏感，且一旦叠加就无法"取最强"（无法从 70% 反推应取 40%）。
- **结论的规模意义**（这是本条最重要的部分）：GE 数量恒定，直接带来三个收益——**属性聚合开销恒定**（不随来源数增长）、**复制量恒定**、**账本裁决复杂度可控**。这条把"正确性需求"和"规模需求"统一起来了，是本设计的关键闭环。

### D6 — 批量结算路径

AOE / 多目标场景走 `ResolveBatch()`：一次域规则查找、一次账本锁定、批量裁决、批量落地，并支持"目标上限与优先级截断"（只结算最近的 N 个）。

- **替代：循环调用单点裁决。** 否决——50 个目标 = 50 次规则查找 + 50 次账本访问 + 50 次落地，重复开销占总耗时的大部分；且无法做"跨目标的全局上限"（如"全场最多 10 个被眩晕"）。
- **结论**：批量与单点**共享同一裁决函数**（保证语义一致，避免两套逻辑漂移），批量只优化外围开销，并额外支持跨目标的全局约束。

### D7 — 技能数据与 UAsset 分离，编译产物可热更新

编辑器产出 `UAKAbilityAsset`（权威、可 diff、进 Git）；构建期编译为紧凑运行时定义（`UAKAbilityDefinition`），运行时**只加载需要的定义**，支持按场景/角色流式加载与**运行时热替换**。

- **替代：运行时直接加载 UAsset。** 否决——UAsset 加载开销大、不能热更新（不停机替换）、且 10⁴ 量级无法全常驻。
- **替代：完全放弃 UAsset，只留 Json。** 否决——失去编辑器的可视化编排与资产校验能力，那是 UAK 的核心价值。
- **结论**：**资产是编辑期真值，编译产物是运行期真值**。二者由构建/导出步骤连接；Json 双向序列化正好是这个连接点的现成实现。

### D8 — 域配置版本化 + 热重载 + 迁移策略

域配置带版本号；热重载时，正在生效的状态按配置的**迁移策略**处理：`Keep`（按新规则重新裁决）/ `Preserve`（保持原值直到自然结束）/ `Expire`（立即到期）。未指定时默认 `Keep` 并记录。

- **替代：热重载时直接丢弃全部状态重算。** 否决——战斗中突然清空 boss 的 debuff 会直接破坏战斗。
- **替代：禁止运行时热重载，只停机更新。** 否决——不符合 MMO 可用性要求。
- **结论**：热重载必须**显式声明迁移策略**，且重载事件写入 Trace 便于事后复盘。这是"不停机更新"与"战斗不被破坏"之间的唯一平衡点。

### D9 — 相关性与 LOD 决定复制的频率与精度

复制视图按 `UAKRelevancePolicy` 分级：完全相关（自己 / 目标 / 队友）→ 全量 + 高频率；视野内 → 全量 + 低频率；视野外但有团队关系 → 仅关键状态；无关 → 不更新。剩余时间**量化**（如 0.1s 粒度）以减少抖动导致的重复发送。

- **替代：所有状态对所有客户端一视同仁地复制。** 否决——MMO 下带宽直接失控。
- **替代：完全交给 UE 的 NetRelevancy。** 部分采纳——UE 的相关性用于**连接级**判定，UAK 在此基础上做**状态级**的精度与频率分级，两者是不同层次，不冲突。

### D10 — 固定步长保证确定性与可回放

所有时间推进、到期判定、裁决都基于固定步长与整数化的 tick 计数，不使用可变 `DeltaTime` 直接参与状态计算。

- **替代：沿用可变 DeltaTime。** 否决——帧率波动会导致到期时间漂移，进而使战斗不可回放，也让 fuzz 与离线仿真失去意义。
- **结论**：固定步长是 **D11（离线仿真）与 fuzz 可复现** 的前提，不是可选的优化。

### D11 — 离线仿真是一等公民

提供 `UAKSimulationHarness`：headless 加载技能定义 + 战斗脚本（谁在什么时候对谁施放什么），批量重跑，产出**状态快照序列**与统计（DPS、控制覆盖率、状态层数分布）。用于：改动后的回归比对、平衡分析、以及把线上战斗日志拿回来重放。

- **替代：只靠运行时测试与人工走查。** 否决——上万技能的组合无法靠人覆盖；且"数值回归"（改了一个技能导致另一场战斗失衡）只有在批量仿真下才能被发现。
- **结论**：仿真与 fuzz 是互补的两层——fuzz 撞不变量（正确性），仿真比对快照（预期不被意外改变）。

### D12 — 预算与降级是显式机制

系统定义 CPU / 带宽 / 更新频率预算；超预算时按**固定顺序**降级（先降低无关实体的更新频率 → 再降低远处实体的裁决精度 → 最后拒绝非关键申请），并持续记录降级事件。

- **替代：不做预算，靠优化硬扛。** 否决——MMO 的负载尖峰（攻城、世界 boss）必然超出任何固定优化能扛的范围，没有降级策略就会雪崩。
- **替代：超预算时随机丢弃。** 否决——不可预测的行为比性能问题更糟；降级顺序必须是**确定且可观测**的。

### D13 — 阶段操作 API 支撑 boss 战

提供状态集合操作：`ClearDomain`（清空某域全部层）、`GrantImmunity` / `RevokeImmunity`、`OverrideDomainRules`（阶段级规则覆盖）。规则覆盖采用"全局规则 + 阶段覆盖"的叠加模型，覆盖层有明确的作用域与生命周期。

- **替代：让 boss 阶段切换靠一个个申请/移除来模拟。** 否决——阶段切换是**集合级**语义，逐个操作既慢又容易漏（漏一个 debuff 就是 bug）。
- **结论**：集合操作是 boss 战的刚需，且必须是原子性的（要么全清，要么不清）。

### D14 — 三层验证：不变量 / fuzz / 仿真

不变量（性质）由 fuzz（随机组合）与仿真（真实战斗脚本）共同验证；规模相关的性质（Tick 数、复制字节数、裁决耗时）也作为**预算型不变量**纳入。

### D15 — 治理能力必须支持增量

静态扫描支持增量（只扫变更资产）+ 索引持久化；Trace 分级采样；否则在 10⁴ 技能与上千克实下不可行。

## Risks / Trade-offs

| 风险 | 影响 | 缓解 |
|---|---|---|
| **R1 复制视图与 ASC 变成两套真值** | 客户端显示与实际状态不符，且难以排查 | 边界写死在文档与类型上：视图只读、只能由账本派生、服务器随时可从账本重建；用不变量持续断言"视图 == 账本投影" |
| **R2 实例休眠导致到期时间不准** | 状态晚一拍到期 | 到期由时间轮按固定步长触发，误差上界是 1 个 tick 且可预期；用不变量断言"到期不早于应到期时间" |
| **R3 对象池化引入脏状态泄漏** | 跨施放的诡异 bug | 归还时强制重置；用不变量断言"新取用的实例处于初始态"；池的取用/归还有计数可查 |
| **R4 热重载破坏进行中的战斗** | 最严重：线上事故 | 强制显式迁移策略；重载事件全量记 Trace；提供 dry-run 模式（先在仿真里跑一遍重载） |
| **R5 批量与单点语义漂移** | 同样输入在两条路径下结果不同 | 强制共享同一裁决函数；fuzz 随机切换批量/单点路径并比对结果 |
| **R6 降级策略被滥用，玩家体验不可预测** | 关键时刻状态不更新 | 降级顺序固定且可观测；关键状态（自己身上的硬控）永不降级 |
| **R7 分层带来的概念负担** | 学习成本与实现量上升 | 分层但不止血：每层都可独立验收、可独立降级（不做 L3 就是当前行为 + 无规模能力） |
| **R8 与宿主既有 Buff 系统双轨** | 两套状态不一致 | 仲裁只处理"由 UAK 技能申请"的状态；宿主自有系统不受影响；提供查询接口与适配层 |
| **R9 规模优化的收益依赖真实负载** | 优化方向可能做错 | 每个规模能力都配可测量的不变量（Tick 数 / 字节数 / 耗时），先测量再优化 |

## Migration Plan

分五个可独立合并、可独立回滚的阶段。每阶段都有明确的可测量验收。

- **P0 — 结算地基**：域配置（版本化）+ 归属账本 + Tag 归属计数（opt-in）+ 默认域。存量行为不变。
  验收：归属类用例通过；既有 36 用例全绿；引入 Tick 数与耗时基线测量。
- **P1 — 仲裁核心 + 聚合**：裁决器 + `ApplyStatus` + 优先级 / 免疫 / 四种聚合 / 上限 / 递减。
  验收：优先级与免疫场景通过；**同类 GE 数量恒为 1**；`UAKDemo` 有可运行范例。
- **P2 — 规模内核**：固定步长时钟 + 事件调度 + 实例休眠 + 对象池化 + 批量结算。
  验收：1000 并发施放下 Tick 数与耗时在预算内（对比 P0 基线）；批量与单点结果一致（fuzz 交叉验证）。
- **P3 — 复制与可用性**：复制视图 + 相关性/LOD + 热重载与迁移策略 + 预算与降级。
  验收：带宽测量在预算内；热重载在仿真中 dry-run 通过；降级顺序可观测。
- **P4 — 治理与观测**：Trace 分级采样 + 离线仿真 + 回归比对 + 增量扫描 + CI 门禁。
  验收：改动一个技能后仿真能发现预期内的快照差异；CI 能阻断冲突。

**灰度**：先在 `UAKDemo` 与单场 boss 战示例上启用，再推广到 Lyra 宿主。

**回滚**：所有新能力默认关闭；停用域配置即回退到当前行为；调度器可整体切回"每帧 Tick"兼容模式（用于线上应急）。

## Open Questions

- **Q1 客户端状态预测的取舍**：服务器权威下状态结算的延迟是否可接受？若要预测，需要把裁决函数与账本快照一起纳入 `FPredictionKey` 回滚，复杂度显著上升。建议 P3 后再评估，先以"表现层预测、状态不预测"运行。
- **Q2 聚合落地的两种实现**：档位 GE（多个预置 GE 资产）vs 单 GE + SetByCaller。后者资产少、热更新友好，**倾向后者为主**，但需先验证宿主工程 GE 是否都能用 SetByCaller 表达。
- **Q3 固定步长的具体频率**：30Hz / 20Hz / 与 DS tick 对齐？需要与宿主的 `NetUpdateFrequency` 与 DS 帧率一起定，建议做成可配置并测量后定默认值。
- **Q4 相关性与宿主 AOI 的对接**：是复用宿主的 AOI 系统，还是 UAK 提供适配接口由宿主注入？倾向**后者**（UAK 定义接口，宿主实现），以保证零宿主改动。
- **Q5 编译产物的格式**：FlatBuffers / 自定义二进制 / 紧凑 Json？需要在加载速度与可调试性之间权衡，建议先做 Json（可 diff、可调试），测量后决定是否换二进制。
- **Q6 归属者跨服务器边界**：跨服 / 分线场景下，归属者标识必须是全局唯一且可序列化，需确认 ID 方案（实例 ID 是否会回绕）。
- **Q7 预算阈值的默认设定**：依赖真实负载数据，P2/P3 测量后校准，不建议一开始就定死。
